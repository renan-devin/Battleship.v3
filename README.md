# Battleship.v3

Browser and Android implementation of the classic Battleship game, built with vanilla
JavaScript (ES modules), Vite and Capacitor. v3 is a standalone fork of
[Battleship.v2](https://github.com/renan-devin/Battleship.v2) that adds a player profile, a
ranking against the AI and Google Play packaging, and is prepared for a future online mode.

## What is new in v3

- **Commander profile.** The game asks for a name before the first match and signs the
  battle reports with it. The profile (`id` + `name`) lives in `localStorage` under
  `battleship.v3.profile` and can be renamed from the header.
- **Ranking and statistics.** Every finished match against the AI is recorded (win or loss,
  difficulty and the number of shots you fired) under `battleship.v3.stats`. The ranking
  panel sorts commanders by wins and then by efficiency (lowest average shots per win, then
  the fewest shots in a single win), shows wins, losses, best and average shots, and can be
  filtered by difficulty.
- **Repository abstraction.** `src/main.js` never touches `localStorage` directly: the match,
  the profile and the statistics go through `src/state/repository.js`. A future
  `RemoteRepository` backed by an HTTP API only needs to implement the same methods.
- **Android app.** Capacitor wraps the production build into a native Android project in
  `android/`, ready for the Play Store. Everything works offline.
- **Isolated storage.** Match saves use `battleship.v3.match` (version 3), so v2 and v3 can
  coexist in the same browser without touching each other's data.

## How to play

1. **Deploy.** Pick a ship from the fleet roster, press `R` (or the orientation button) to
   rotate it and click a cell on your board. `Random` deploys the whole fleet, `Reset`
   clears the board and clicking a placed ship takes it back.
2. **Fight.** Press `Start Battle` once the fleet is ready and click a cell on the enemy
   board to fire. Misses show a sonar ring, hits a burning cross, and a ship is revealed
   when it sinks. The enemy answers after a short delay.
3. **Finish.** The battle ends as soon as one of the fleets is completely sunk; the battle
   report offers a new game.

The status bar shows whose turn it is and the outcome of the last shot, and mirrors both to
an `aria-live` region.

## Difficulty

The selector is locked once the battle starts, and the status bar shows which opponent is
in play.

- **Easy** fires at a random untouched cell.
- **Hard** hunts: it sweeps a parity mask no surviving ship can straddle and, as soon as a
  ship is damaged, works that contact out - the gap between two aligned hits first, then
  the ends of the inferred line, then the neighbours of a lone hit - and only resumes the
  sweep once the ship is sunk.

## Saved matches

The match is written to `localStorage` under `battleship.v3.match` after every move, so a
reload picks it up where it stopped and the status bar shows a `Resumed` chip. A reload
during the enemy reply restores the pending enemy turn, which then fires once. `New Game`
wipes the save. A save that is unreadable, from another version or inconsistent with the
engine rules - a ship off the board, overlapping ships, a repeated shot, a hit that does
not match the fleet, a winner nobody earned - is discarded and the game starts fresh.

## Profile, statistics and ranking

- `src/state/profile.js` creates, validates, loads and saves the commander profile
  (`createProfile`, `renameProfile`, `loadProfile`, `saveProfile`, `clearProfile`).
- `src/state/stats.js` builds one record per finished match (`createMatchRecord`), keeps the
  history (`recordMatch`, `loadStats`, `saveStats`), summarises a profile
  (`summarizeProfile`) and ranks every profile (`rankProfiles`).
- `src/state/repository.js` exposes `createLocalProfileRepository`,
  `createLocalStatsRepository` and `createLocalMatchRepository`, all backed by an injected
  `Storage`. Their methods are asynchronous so a remote implementation can replace them
  without changing the game.

All three modules are pure (no `document`/`window`), store versioned JSON envelopes,
validate everything they read and are covered by `tests/profile.test.js`,
`tests/stats.test.js` and `tests/repository.test.js`.

then builds and publishes the site.

## Android (Google Play) with Capacitor

The native project in `android/` is generated by Capacitor from `capacitor.config.json`
(`webDir: dist`, app id `dev.renan.battleship`). The web bundle is copied into the APK, so
the game runs fully offline; profile, statistics and the saved match stay in the WebView's
`localStorage`.

```bash
npm run build                 # production bundle in dist/
npx cap sync android          # copy dist/ into android/ and update native plugins
npx cap open android          # open the project in Android Studio
# or, in one go:
npm run cap:sync && npm run cap:open
```

To publish on the Play Store:

1. Bump `versionCode` / `versionName` in `android/app/build.gradle`.
2. In Android Studio choose **Build > Generate Signed Bundle / APK**, pick **Android App
   Bundle**, create or select your upload keystore and build the `release` variant. The
   `.aab` lands in `android/app/release/`.
3. Upload the bundle in the Google Play Console (**Release > Production > Create new
   release**), fill in the store listing and roll it out.

From the command line the same bundle is produced with
`cd android && ./gradlew bundleRelease` once a signing config is set in
`android/app/build.gradle`. Debug builds for a device or emulator:
`./gradlew assembleDebug` then `adb install app/build/outputs/apk/debug/app-debug.apk`.

## Project structure

```
src/
  engine/   Game rules and board logic (pure logic, no DOM)
  ai/       Opponent strategies (pure logic, no DOM)
  state/    Orchestration between engine, AI and UI (pure logic, no DOM)
    persistence.js  Saved match envelope
    profile.js      Commander profile
    stats.js        Match history, summaries and ranking
    repository.js   Data-source boundary (local today, remote tomorrow)
  ui/       DOM rendering helpers
  main.js   Entry point that wires state, engine, repositories and DOM
tests/      Vitest test suite
android/    Capacitor Android project
docs/       Debugging report
```

## Placement rules

Ships must stay inside the board, must not overlap and can only be placed horizontally or
vertically. Ships may touch each other, side by side or diagonally.
